# wukong-bench-runner

Сделал консольное приложение на C# (.NET 8), которое само гоняет Black Myth: Wukong Benchmark Tool из Steam
двумя проходами: сначала проход, где нагрузка должна лечь на процессор, потом проход, где нагрузка ложится
на видеокарту. Приложение само находит игру, само пишет настройки в её конфиг, само проходит меню бенчмарка и
само дожидается результата и само разбирает JSON, который бенчмарк оставляет в каталоге префикса Proton.
От лаунчера Steam до двух готовых отчётов — одна команда.

## Что получилось

Полный прогон — одна команда, она сама всё делает и кладёт два отчёта в `results/<дата-время>/`:

```bash
dotnet run --project src/WukongBenchRunner -- run
```

Одиночный замер неустойчив, поэтому у каждого прохода есть повторы: `--repeat 3` прогоняет каждый профиль
три раза и в отчёт кладёт медиану, минимум, максимум и разброс по серии.

Результат на моём ноутбуке: медиана **13.0 FPS** в CPU-тесте и **3.0 FPS** в GPU-тесте на Ryzen 5 5625U
со встроенной Radeon Barcelo, по три прогона на проход. Изоляцию процессора проверил контрольным прогоном
при 25% масштаба рендера — результат не изменился, значит видеокарта кадр не ограничивает. Подробности и
оговорки ниже, в том числе почему это число нельзя читать как чистую скорость процессора.

Посмотреть отчёт на настоящих данных можно вообще без Linux, без игры и без Steam — файлы результатов
одного моего прогона лежат в `samples/`:

```bash
dotnet run --project src/WukongBenchRunner -- report \
  --from-results samples/cpu_raw.json samples/gpu_raw.json
```

Эта команда работает на Windows и macOS: .NET 8 SDK остаётся единственным требованием.

Полный автоматический прогон требует сессии X11 с расширением DRI3, об этом отдельный раздел ниже.

## Что внутри

Задание операционную систему не задаёт, а способ запуска нужно выбрать самому, и я выбрал то, на чём
уже работаю: это мой ноутбук с Linux, Ubuntu 24.04.3. Бенчмарк сам по себе Windows-приложение, поэтому
на Linux он запускается через Proton Experimental 11.0-100, и это добавило пару неприятных особенностей,
о которых я пишу ниже.

На Windows было бы заметно проще: бенчмарк там нативный, и в его отчёте живые метрики времени кадра по
CPU и GPU, из которых сразу видно, кто ограничивает кадр. Под Linux эти поля недоступны, поэтому часть
выводов приходится делать косвенно — ниже покажу, как именно. 
Мое решение экстравагантное, но кто-то ведь должен и на Linux играть в Windows-игры и использовать
бенчмарки для проверки характеристик и настроек под конкретную сборку. 

Прогонял на окне 1920×1200, встроенная графика AMD Radeon Barcelo (RADV RENOIR), процессор
Ryzen 5 5625U, сессия X11 (в Wayland XWayland может подняться без DRI3, и тогда игра не запустится —
об этом ниже).

## Как запустить

Полный прогон требует Linux, .NET 8 SDK или новее, `xprop` и `xwininfo` (пакет `x11-utils`), 
запущенный Steam с установленным Black Myth: Wukong Benchmark Tool (AppID 3132990, бесплатный). 
Первый раз игру надо запустить вручную: бенчмарк при первом старте создаёт свой `GameUserSettings.ini` 
и компилирует шейдеры, а инструмент правит уже существующий конфиг.

```bash
sudo apt install x11-utils          # если ещё не стоит

git clone https://github.com/Fisher48/wukong-bench-runner.git
cd wukong-bench-runner
dotnet test                          # 99 тестов, Steam и игра для них не нужны
dotnet run --project src/WukongBenchRunner -- inspect   # что найдено и готово ли окружение
dotnet run --project src/WukongBenchRunner -- run       # основной сценарий, ~8 минут
```

`inspect` стоит выполнить до прогона: он показывает, какие пути найдены, какая версия Proton, работает ли
ввод, не запущен ли бенчмарк уже сейчас. `run` — это и есть тот самый автоматический сценарий из задания:
два прохода подряд, восстановление настроек и отчёт. Если результаты уже есть на руках и запускать игру
не хочется, отчёт пересобирается из файлов: `report --from-results cpu.json gpu.json`.

Готовый бинарник, если не хочется возиться со сборкой:

```bash
dotnet publish src/WukongBenchRunner -c Release -r linux-x64 --self-contained false -o dist
./dist/WukongBenchRunner run
```

Во время прогона мышь и клавиатуру лучше не трогать: окно бенчмарка должно оставаться в фокусе, иначе
эмуляция ввода до него не дойдёт.

Всё, что чаще всего нужно поправить, собрано в параметры:

- `--only cpu|gpu` — выполнить один проход вместо двух
- `--cpu-render-scale <процент>` и `--gpu-render-scale <процент>` — переопределить масштаб рендера в нужном проходе
- `--gpu-raytracing` — включить трассировку лучей в GPU-тесте
- `--timeout <минут>` — таймаут одного прохода, по умолчанию 15
- `--render-height <пиксели>` — высота окна для расчёта рендера, если не определилась сама
- `--window-timeout <секунды>` — сколько ждать окна бенчмарка, по умолчанию 300
- `--install-dir`, `--steam-root`, `--history-dir` — указать пути руками, если Steam лежит не в типовом месте
- `--start-mode auto|flag|menu` — как запускать тест: движковым флагом, кликами по меню или флагом со страховкой
- `--flag-timeout <секунды>` — сколько ждать результат от флага, прежде чем включить клики, по умолчанию 30
- `--layout-start-x/y`, `--layout-confirm-x/y` — координаты кнопок меню в долях окна (нужны только в режиме `menu`)
- `--keep-config` — не восстанавливать исходный `GameUserSettings.ini`
- `probe` с `--press-return`, `--click x,y`, `--keep` — диагностика ввода: показать окно и кликнуть в нужную точку

## Как я выбирал настройки CPU-теста

Главная задача прохода — чтобы кадр ограничивал процессор, а видеокарка была по возможности незаметна.
Отсюда три решения, которые в сумме и дают профиль:

**Масштаб рендеринга 50%.** Это главный рычаг. На этой сцене кадр на процессоре занимает десятки
миллисекунд, а видеокарта на полном разрешении умудряется уложиться в пару. Уменьшение числа пикселей
в четыре раза оставляет GPU примерно 1–2 мс на кадр — то есть она перестаёт быть ограничителем. Проверяется
это отдельно, см. ниже.

**Качество 1 в меню и sg.*=0.** Убирает всё, что нагружает GPU в основном: тяжёлые тени, глобальное
освещение, отражения, растительность, постобработку. Логика бенчмарка (анимации, физика, спавн, сборка
draw calls) от разрешения и качества не зависит — она живёт на CPU.

**Всё, что умеет искусственно повышать FPS, выключено.** Генерация кадров — самое важное: она дорисовывает
кадры без участия процессора и в CPU-тесте просто выдавала бы чужой результат. Сюда же трассировка лучей
(она почти целиком грузит GPU), апскейлер (иначе внутреннее разрешение задаёт DLSS/FSR, а не я),
VSync и ограничение FPS (иначе FPS упрётся в 60 Гц монитора, а не в процессор).

Разрешение окна я не трогаю вообще: его выбрал сам бенчмарк при первом запуске под конкретный экран,
и подставлять туда пресеты своего монитора смысла нет — на другом экране такой комбинации может просто
не быть. Уменьшать окно ради экономии GPU тоже незачем, потери и так достаточно за счёт масштаба рендера,
а вот меньшее окно само по себе замедляет CPU (ввод, презентация кадра), что для этого прохода нежелательно.

Высота рендера считается от высоты окна: `ImageQuality = окно × масштаб`. На моём экране 1200 px это даёт
600 px при 50% и 1200 px при 100%, на экране 1080p будет 540 и 1080. Если разрешение определить не вышло
(например, нет `xrandr`), инструмент не станет писать в конфиг придуманное число, а попросит указать
высоту через `--render-height`. И после каждого прохода сверяет, что бенчмарк реально применил запрошенный
масштаб: JSON бенчмарка содержит фактический процент, и если он разошёлся с тем, что мы просили, в лог и
в `environment.txt` падает предупреждение.

## Как я выбирал настройки GPU-теста

Здесь обратная задача — вдарить по видеокарте так, чтобы загрузка была максимальной, а FPS отражал именно
GPU. Поэтому 100% масштаба рендера при выключенном апскейлере (каждый пиксель считается нативно, без
скрытого понижения внутреннего разрешения) и качество 5 в меню при sg.*=4 — самые тяжёлые тени, GI,
отражения, растительность и постобработка. Генерация кадров, VSync и ограничение FPS выключены по тем же
причинам, что и в CPU-тесте: дорисованные кадры и ожидание vsync показывают не производительность GPU.

Трассировку лучей по умолчанию выключил, и на этом ноутбуке включить её нечем: в Barcelo нет RT-ядер,
это графика на Vega в Ryzen 5000. Я ставил `Rtx=2` в конфиг вручную, и бенчмарк вернул 0 — то есть это
ограничение железа, а не особенность движкового флага. Поэтому режим с трассировкой я **не проверял**: он
есть в инструменте как флаг `--gpu-raytracing` (ставит `Rtx=1`, `RtxLevel=2`, `sg.RayTracingQuality=2`),
но подтвердить его работоспособность на своём ноутбуке я не могу. Из общих соображений он всё равно
выключен по умолчанию: неподдерживаемое значение роняет бенчмарк на старте, а разные реализации
трассировки делают результаты несопоставимыми между видеокартами. Если будете запускать инструмент на карте
с RT, проверьте этот флаг первым делом.

Оба прохода отличаются только нагрузкой на графику, а результат отличается в 4.33 раза (13.0 против 3.0 FPS) —
это хороший признак, что настройки действительно задают разные режимы, а не отличаются косметически.

## Как я проверил, что CPU-тест не упирается в GPU

Проценты загрузки видеокарты у AMD из `/sys/class/drm/card0/device/gpu_busy_percent` показывают занятость
любого движка, а не степень его загрузки, поэтому в CPU-проходе там 90+%, и это нормально — это не значит,
что кадр ограничивает видеокарта. Проверить пришлось экспериментом: прогнал CPU-проход с `--cpu-render-scale 25`,
то есть в четыре раза меньше пикселей, чем в основном 50%-проходе.

```
  50% (основной проход)   960 x 600   13.0 FPS  (медиана из трёх: 14, 13, 13)
  25% (контрольный)       480 x 300   14.0 FPS
```

Пикселей стало в четыре раза меньше, а результат упал внутрь разброса основной серии, то есть не изменился.
Значит видеокарта в этом проходе не ограничивает кадр, и FPS здесь не про графику. Заодно это и ответ на вопрос «а не мало ли
50%»: ниже уже нет смысла опускаться, а выше видеокарта начинает забирать секунды кадра на себя.

Но называть это число чистой скоростью процессора нельзя, и тут я сначала ошибся. По данным самого
бенчмарка в CPU-проходе процессор занят 13.2 мс, а кадр длится 72.3 мс — то есть около 59 мс приходится
не на процессор и не на видеокарту. Масштаб рендера на них не влияет, поэтому это не работа GPU. Похоже,
это накладные расходы Proton и путь вывода кадра через Vulkan. То есть 13.0 FPS измеряют не процессор сам
по себе, а весь конвейер Linux + Proton, и накладная часть тут больше половины кадра. На Windows такого
накладного расхода нет, и там к CPU-проходу отношение строже.

Почему проверка построена именно так. У Benchmark Tool в `Records` есть поля `CPUFrameTime` и
`GPUFrameTime`, и на первый взгляд это прямой ответ на вопрос, кто тратит время на кадр. Разбирая свои
же файлы результатов, я нашёл, что под Proton они ведут себя по-разному. `CPUFrameTime` настоящий:
медиана 13.2 мс в CPU-проходе и 15.7 мс в GPU-проходе, что логично — во втором больше работы на стороне
процессора. А `GPUFrameTime` просто повторяет обратную величину FPS: 67.2 мс при кадре 72.3 мс в
CPU-проходе и 298.0 мс при кадре 306.7 мс в GPU-проходе. Это длина кадра, а не работа видеокарты, и
определить по нему узкое место нельзя. Единицу возвращают только сводные счётчики `CPUAvg`, `GPUAvg`,
`GPULeak` и `CPUUsage`/`GPUUsage` из `Records` — это счётчики Windows Performance Counters, из wine они
недоступны.

Отсюда решение: `CPUFrameTime` использовать можно и я его показываю в отчёте, а для проверки изоляции
остаётся косвенный способ — убрать почти всю работу видеокарты и посмотреть, изменится ли FPS. Не
изменился — значит кадр уже не про графику.

Ещё одну попытку я сделал и откатил. Логично же для CPU-теста не облегчать сцену, а наоборот её
утяжелить: поднять дальность прорисовки и плотность растительности до максимума, чтобы объектов в кадре
стало больше и процессору было тяжелее. Сделал через переопределения отдельных групп качества, прогнал
трижды: FPS упал с 13 до 12, а `CPUFrameTime` не вырос, а упал с 13.2 до 14.9 мс — то есть лишняя сцена
добавила нагрузку, но не ту, которую бенчмарк измеряет, и оценку процессора только ухудшила. Профиль
вернулся к минимуму, а механизм переопределения остался в инструменте.

Оговорка про чужое железо: проверка выше — про мой ноутбук с встроенной Barcelo. На более мощной видеокарте
50% масштаба может уже не снимать её с критического пути, и тогда CPU-тест покажет FPS ниже реального
предела процессора. Профили под железо не подстраиваются: GPU-тест и так собран на максимуме (100% рендера
плюс максимум качества), а для CPU-теста масштаб задаётся вручную через `--cpu-render-scale`, и тот же
контрольный прогон покажет, хватает ли его на этом ноутбуке.

## Как устроен автоматический сценарий

Ниже весь путь от одной команды до двух отчётов — с этим пришлось разобраться в основном, потому что
Benchmark Tool не документирован и никаких ключей запуска не имеет.

**Поиск игры.** Иду от Steam в типовые места (`~/.steam/steam`, `~/.local/share/Steam`, snap, flatpak),
читаю `steamapps/libraryfolders.vdf` — из него путь к библиотеке, дальше `steamapps/common/appmanifest_3132990.acf`
и из него `installdir`. Там же находится `b1/Saved/Config/Windows/GameUserSettings.ini` и, в
`steamapps/compatdata/3132990/pfx`, каталог с результатами прошлых прогонов. Никаких захардкоженных путей.

**Запуск.** `steam -applaunch 3132990`. Дальше жду не сам процесс Steam, а `b1-Win64-Shipping.exe`
(внутри это `wine64-preloader ... b1-Win64-Shipping.exe`) и нахожу его окно через `xwininfo`, сверяя
`_NET_WM_PID` — так окно игры находится однозначно, а не «первое похожее на бенчмарк». Под Proton процесс
пришлось искать именно по `argv[0]` из `/proc/<pid>/cmdline`: поиск по имени процесса давал ложные
срабатывания на другие окна того же приложения.

**Запуск теста.** Основной путь — движковый флаг `-benchmark`:

```bash
steam -applaunch 3132990 -benchmark
```

Это штатный аргумент Unreal Engine, и Benchmark Tool на нём стартует сразу, минуя заставку и меню. Я
проверил это на своём ноутбуке: файл результата появляется сам, без единого нажатия. Плюс ровно тот же, что
и при кликах: 14.0 FPS в CPU-тесте и 3.0 в GPU-тесте. Настройки при этом уважаются — и масштаб рендера,
и уровень качества, и все десять групп `sg.*`, я специально проверял это на двух прогонах с разными
профилями. Выигрыш здесь не в скорости, а в воспроизводимости: во время измерения не происходит ни одного
постороннего нажатия.

Как инструмент понимает, что флаг сработал. Пока тест идёт, процесс бенчмарка набирает процессорное время;
пока он стоит на заставке и ждёт нажатия — почти не набирает. Поэтому я сравниваю процессорное время между
двумя замерами: выросло больше чем на 0.4 секунды за цикл опроса — значит кадры считаются, и инструмент
просто ждёт результат. Первыми деталями я сделал чистую проверку по времени и получил 44 лишних клика за
прогон, потому что сам тест идёт три с половиной минуты; критерий по активности процесса это убирает.

**Страховка.** Если флаг по какой-то причине не сработал — например, на другой версии сборки — инструмент
это заметит по простою процесса и переключится на прежний путь: ввод через XTEST (`libX11` + `libXtst`,
P/Invoke) и клики по координатам, `Enter` на заставке, «Тест быстродействия» (0.115 / 0.452), «Подтвердить»
(0.393 / 0.580). Сценарий тот же, что был у меня до флага: каждые 3 секунды, пока не появится файл
результата. Координаты заданы долями окна, а не пикселями, поэтому работают при любом разрешении. Режим
выбирается `--start-mode auto|flag|menu` (по умолчанию `auto`), окно нажатия при флаге задаёт
`--flag-timeout`.
Если процесс всё же закрылся (например, клик угодил в «Выйти» — так бывает, когда окно ещё не прогрузилось),
инструмент перезапускает бенчмарк, до трёх попыток.

**Ожидание результата и разбор.** Успех прогона определяется по появлению нового файла в
`.../Temp/b1/BenchMarkHistory/Tool` — имя файла это unix-время старта прогона, расширения нет. Дальше
разбирается JSON: забираю `FPSAvg`, `FPSMax`, `FPSMin` и всю строку `Records`, из которой сам считаю
медиану, 95-й перцентиль, 1% low, 0.1% low и среднее время кадра.

**Про метрики бенчмарка под Proton.** В JSON есть поля `CPUAvg`, `GPUAvg`, а в `Records` — `CPUUsage` и
`GPUUsage`, но под Proton они всегда равны 1%: счётчики Windows Performance Counters из wine недоступны.
`CPUFrameTime` и `GPUFrameTime` тоже с FPS не сходятся. Показывать 1% в отчёте я не стал — вместо этого
замеряю загрузку сам, раз в секунду читая `/proc/stat` и `gpu_busy_percent`, и в отчёт кладу и то и другое,
с явной оговоркой, что `gpu_busy_percent` у AMD означает занятость любого движка. Итоговый FPS считается
только по полям `FPS*` и по `Records` — им можно доверять.

**Настройки игры не должны пострадать.** В `GameUserSettings.ini` меняются только нужные ключи в
`UISettingData` и `[ScalabilityGroups]`; остальные ключи, включая метрики прошлых прогонов, не трогаются.
Отдельно не трогаются `ScreenMode`, `ScreenRatio` и `ScreenResolution`: разрешение окна остаётся таким,
как его выбрал бенчмарк при первом запуске на этом экране.
Перед первым проходом делается копия, после последнего — восстановление. Причём процесс бенчмарка закрывается
принудительно, через `SIGKILL`: если закрыть его мягко, игра успевает записать в конфиг свои (уже загруженные
из моего конфига) значения и весь аккуратный патч теряется. На всякий случай восстановление проверяет файл
побайтно и повторяет попытку, если игра всё же успела что-то дописать.

```
src/WukongBenchRunner/

  Cli/CommandLineOptions.cs       разбор аргументов и их проверка
  Discovery/                      VDF/ACF-парсер и поиск Steam, игры, каталога результатов
  Config/                         INI-редактор, точечный патч настроек, бэкап и восстановление
  Profiles/ProfileCatalog.cs      два прохода и текст с обоснованием настроек
  Running/                        запуск через Steam, работа с процессами, поиск окна,
                                  запуск флагом -benchmark, ввод через XTEST как страховка
  Results/ResultParser.cs         разбор JSON и статистика по массиву Records
  SystemInfo/                     характеристики ПК, замер загрузки CPU/GPU, проверки графики
  Reporting/                      консольный отчёт, report.md и report.json
  SystemInfo/GraphicsDiagnostics  проверки DRI3/XTEST/DRM, без которых Proton не запустит игру

results/<дата>/                   отчёты, сырые JSON, логи прогонов
```

## Тесты

```bash
dotnet test
```

99 тестов, которые не требуют ни Steam, ни игры. Парсеры проверяются на настоящих файлах, снятых с этого
ноутбука: `GameUserSettings.ini`, `appmanifest_3132990.acf`, `libraryfolders.vdf`, вывод `lspci -k -nn` и
`xwininfo -root -tree`, JSON результата бенчмарка. Отдельно тесты надёжности: дубликаты ключей в INI,
поиск процесса по `argv[0]`, коды возврата, `--keep-config`, восстановление конфига, которое игра
пытается перезаписать, определение DRI3 по выводу `xdpyinfo`, ожидание устойчивого клиента Steam
отбрасывание чужих окон при поиске по заголовку, отличение клиента Steam от reaper и steam-launch-wrapper,
расчёт высоты рендера от разрешения экрана и сверка того, что бенчмарк реально применил запрошенный масштаб.

## Если игра выходит сразу после старта

Самая неприятная грабли, на которую я наступил на своём ноутбуке. После перезагрузки XWayland в GNOME
поднялся без расширения DRI3, Proton не смог вывести кадр и писал в лог:

```
vulkan: No DRI3 support detected - required for presentation
```

Дальше игра жила 10–15 секунд и завершалась, Steam при этом показывал код выхода `10`, а инструмент
2 минуты ждал окно у уже мёртвого процесса и падал с общим сообщением про `DISPLAY`.

Проверяется одной командой:

```bash
xdpyinfo | grep -i dri3
```

Если расширения нет — прогон не заработает, причём это не чинится настройками инструмента. Причина
системная: в GNOME на Wayland вложенный XWayland поднимается в режиме rootless, без прямого доступа к
GPU, и расширения DRI3 не получает. Помогает вход в сессию Xorg: выйти из системы, на экране входа
нажать шестерёнку рядом с именем пользователя и выбрать «Ubuntu on Xorg». После этого
`dotnet run -- inspect` должен показать `DRI3: есть`.

Так что если вы работаете в GNOME на Wayland, одного перезапуска приложения недостаточно: сессию надо
переключить целиком, иначе игра будет падать через 10–15 секунд после старта.

Что я добавил после этого случая:

- `inspect` и начало `run` показывают блок «Графика» с DRI3, XTEST, DRM, Vulkan ICD и Steam,
  и предупреждение про код 10, если DRI3 отсутствует;
- при падении игры инструмент сразу выдаёт адресную подсказку про DRI3, а не общее сообщение про
  `DISPLAY`, и не ждёт окно зря — падает в момент исчезновения процесса.

## Вывод

Получился инструмент, который от запуска до двух отчётов работает без участия человека: сам находит игру,
сам пишет настройки, сам проходит меню, сам дожидается результата и сам считает статистику. И отдельно
замерил загрузку CPU и GPU, потому что штатные счётчики бенчмарка под Proton не работают.

Сильные места, как мне кажется: контрольный прогон на 25% масштаба, который снимает главный вопрос
к CPU-тесту, и принудительное закрытие процесса — без этого настройки игры после прогона остаются
в непредсказуемом состоянии.

Отдельно стоит рассказать, как я искал причину падений, потому что первый диагноз у меня был неверным.
Сначала я заподозрил самообновление Steam: клиент после перезагрузки действительно обновляется и
перезапускает себя, и по времени это совпадало с падением игры. Логи Steam это опровергли — обновление
завершилось, а игра умерла уже через минуту и умерла бы в любом случае, всё из-за того же DRI3. Ожидание
«устойчивого клиента» я убрал, оно только тратило по две минуты впустую на каждый проход. А вот поиск
процесса Steam пришлось починить: он сравнивал `argv[0]` с basename и искал `ubuntu12_32/steam` вместо
`steam`, из-за чего `inspect` всегда показывал `Steam запущен: False`. Короче, время на диагностику
потрачено, а ошибка была не там, где я думал.

Чего не хватает и что я сознательно не делал. API у Benchmark Tool по-прежнему нет: общение с результатом
идёт через JSON, который движок сам оставляет в каталоге префикса, а запуск — через флаг `-benchmark`,
который документирован Epic для движка, но не этим приложением. То есть опираюсь на поведение конкретной
сборки `1.0.3.14649`, которую и проверял. Если флаг перестанет работать, инструмент не сломается, а уйдёт
в клики по меню, и тогда разметку придётся править через `--layout-*`; `probe` для этого и нужен.
Ещё одна находка при проверке: игра перезаписывает `GameUserSettings.ini` при выходе, поэтому проверять
настройки в конфиге после ручного прогона бессмысленно — их уже переписали. Инструмент это учитывает:
он снимает копию до запуска и восстанавливает её побайтно с проверкой.
Ввод требует X-сервера, то есть под чистым Wayland без XWayland инструмент не заработает, а скриншоты
окна через XWD под Wayland выходят чёрными — геометрию окна пришлось снимать с пользовательских скриншотов.
Отдельно я не стал усложнять инструмент поддержкой нескольких видеокарт или обхода Steam — задача про два
прохода на одном компьютере, и натягивать на это лишнее смысла нет.

По самому железу результат скромный, но объяснимый: встроенная графика на общей памяти даёт 3.0 FPS
на максимуме, и на 50% масштаба она перестаёт быть узким местом настолько, что кадр целиком упирается
в Ryzen 5 5625U — 13.0 FPS при 6 ядрах и 12 потоках.
